## Spec / logic errors
- Budget policy (§0.5, §4.3) ignores that Part B runs after Part A inside the same 3x clock. The spec says 'Time per video (A + B) at most 3x video duration'. run_submission.py starts t0 just before detect_events. It then decodes every frame with cv2 read() and calls step(), and it empties BOTH events and risk if total_sec > budget. The report says Part A should 'stop and return the events found so far' at 2.4x, which leaves only 0.6x for Part B. That covers the harness's full-resolution decode plus step() with little or no margin, so a late Part A zeroes Part A too. Part A's cutoff has to be about 3x·dur − (measured Part B cost, including harness decode) − margin, and Part B needs its own wall-clock degrade mode (e.g. return the last score cheaply).
- The 'real ways to crash the harness' rationale for the sanitizer (§0.6, §4.4) is wrong for the actual harness. clean_events() coerces with float()/str(), drops NaN or bad times, clamps end to duration and rounds. Risk goes through min(1,max(0,float(score))), which maps NaN to 0.0. The sanitizer's real value is different. Per the FAQ ('Two same-class events at once -> report one segment covering both'), it should merge same-class overlaps, because the harness keeps the earlier segment and drops the later one ('earlier-starting kept'). It should also drop blips.
- The annotation guide example 'congestion: one segment per direction' (§6.2) contradicts the spec. The spec says 'Segments of the same class must not overlap', and the FAQ says 'Two same-class events at once -> report one segment covering both (annotations do the same)'. If both directions are congested at the same time, that must be one merged congestion segment. Otherwise the dev labels are invalid for evaluate.py (overlap error) and predictions lose the later segment.
- Treating harness behaviour as unknown (§4.3 'We don't know whether import time counts', §4.4 'If it enforces the time limit with an exception', §10 Q2/Q5/Q9) is wrong: the starter kit is on disk and answers these. Import/model loading is outside the per-video budget. There is no signal or exception timeout and no kill. The deadline is checked every 100 frames in Part B. An exception in step() discards the whole video's risk curve. t_sec = frame_idx/fps. Harness duration = CAP_PROP_FRAME_COUNT/fps. A new RiskEstimator is built per video.
- Determinism section (§3) contains an error and an outdated item. (a) 'iteration over sets or dicts keyed by strings changes between processes' is false for dicts, which are insertion-ordered; only set/frozenset order depends on PYTHONHASHSEED. (b) The CUBLAS_WORKSPACE_CONFIG=:4096:8 requirement was removed in PyTorch 2.10 (PR #161749). Also, torch.use_deterministic_algorithms(True, warn_only=True) does not make determinism 'structural': non-deterministic kernels still run and only warn. Run CI with warn_only=False to find them.
- VLM time arithmetic (§4.2) is inconsistent. 20 clips × 3–8 s = 0.10–0.27x of a 10-min video (not 0.03–0.09x) and 1.0–2.7x of a 1-min clip (not 0.2–0.5x).
- The IoU tolerance table (§6.3) is presented as 'the largest boundary error that still counts' but omits the tightest case, both ends too narrow. There IoU = (L−2d)/L, so d ≤ L(1−τ)/2: 0.30 s for a 2 s event and 0.75 s for a 5 s event at τ=0.7. So '~0.35 s of error on a 2 s event' overstates the tolerance. Also, with stride 3 at 25 fps, the worst-case snap error per boundary is ≤2 frames (0.08 s), not 0.12 s.
- The requirements.txt header 'Tested on Ubuntu x86_64, Python 3.10-3.13' overstates what was done. Only dependency resolution was checked (uv pip compile / pip --dry-run); nothing was installed and run on Ubuntu.
- Risk register #11 and §12 assume a free Hugging Face CPU Space can host the demo. Creating Gradio or Docker Spaces on CPU Basic now requires a paid plan; free accounts get static Spaces or up to 2 ZeroGPU Gradio Spaces.


## Missing points
- The starter kit and sample-video list are already on disk: C:\Users\Cicada\Desktop\WestHack\wiut_cv_scripts.zip (run_submission.py, evaluate.py, solution.py, requirements.txt = numpy>=1.24 and opencv-python-headless>=4.8, examples/) and C:\Users\Cicada\Desktop\WestHack\Videos.pdf (4 sample videos: C3896, C3897, C3902, C3905). The team context says otherwise, and the report should have been grounded in the real harness code.
- The whole run can be lost at once. run_submission.py writes predictions.json only after ALL videos, and it catches only Exception. Any of these kills the entire submission (model score 0): a segfault in a decoder or native extension, a host OOM-kill (32 GB RAM), a sticky CUDA error (illegal memory access poisons the context, so every later video fails), a SystemExit from a library, or a hang in detect_events (never killed). Mitigations: avoid risky native paths, cap memory, check CUDA health per video, and possibly run heavy optional stages in a subprocess with a timeout.
- Import-time warm-up. Because load_solution() runs before any per-video timer, load all models at import and do the CUDA context init, cuDNN init and a dummy forward there. This takes several seconds of fixed cost out of each video's budget, which matters most for short clips.
- predictions.json from the harness contains a 'log' block with wall-clock timings and a 'team' field (default 'unnamed-team'; the official command passes no --team). Determinism diffs and the rubric's 'results on samples match predictions_samples.json' check must ignore 'log'. Mention this in the README so judges do not see a mismatch.
- Part A and Part B see different decoders. Part B frames come from the harness's cv2.VideoCapture with the default backend. If Part A uses PyAV, pixels, frame counts and timestamps can differ slightly (different bundled FFmpeg/swscale). Use the same decode path, or confirm that thresholds and shared detections are robust to this. Also align Part A timestamps to frame_idx/fps, which is how the harness and the annotation convention define time.
- Determinism performance detail: with use_deterministic_algorithms(True), PyTorch fills uninitialised memory with NaN on every allocation. Set torch.utils.deterministic.fill_uninitialized_memory=False for inference, as Ultralytics does. Also force-set, rather than os.environ.setdefault, any offline env vars the organizers' shell might already define.
- Demo hosting reality. A free HF CPU Space needs a paid plan now. Evaluate alternatives early (ZeroGPU Gradio Space on a free account with its visitor quotas, a small VPS, other PaaS free tiers, or a static site plus a separate inference server). The live demo is 30% of the Website score and must survive the judges' upload.
- Python 3.10.19 is already installed locally via uv. The team can test the organizers' lowest allowed Python (3.10 path: numpy 2.2.6 / scipy 1.15.3) on Windows and in WSL, not just 3.12.
- Kaggle's 2xT4 sessions have fewer CPU cores than the 8-core eval box, so CPU-bound decode and harness read() timings measured on Kaggle will not transfer directly. Calibrate the cost table on both the GPU and the CPU side.
- Expected-value view of per-class gating. A class absent from test but predicted costs roughly Score_A/(|C|+1). A class present in test but never predicted already scores 0. The kill-switch decision should weigh the prior that the class appears ('test videos contain events not in the samples'), not just dev precision, which cannot be measured for classes missing from the samples.
