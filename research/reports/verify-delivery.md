# Verification: verify:delivery

Overall reliability: Mostly reliable. Almost every hosting and platform fact checks out against primary docs as of September 2026: the HF paywall and ZeroGPU rules, HF hardware prices and sleep behaviour, Modal, Vercel, GitHub Pages, Cloudflare, Render, Oracle, Streamlit, Netlify, UptimeRobot, rVFC, mp4v and imageio-ffmpeg. The scoring arithmetic is also right. The weak points are a few technical rationales and design logic. The Gradio version is stale (6.28.0 is out). The reason given for avoiding gr.Video is wrong. The ZeroGPU quota logic is wrong: admission uses the requested duration and the quota belongs to the visitor, so 'many runs' and the replica failover do not hold. The 20 s failover timeout contradicts the 1–2 min wake-up. The AGPL advice clashes with the 'protected' Space advice. The metric-visualisation details are underspecified: no τ for matching, and per-video AP is ill-defined. The priorities and overall architecture are sound, but the demo backend plan should be fixed before anyone builds on it.

## Spec / logic errors
- The ZeroGPU plan misreads the quota rules. The report sets @spaces.GPU(duration=90) and says 'a judge can run it many times' on the 2-minute visitor quota. Admission uses the requested duration, so an unauthenticated judge gets only about 1–3 runs. The Space B replica does not fix this either, because the quota belongs to the visitor, not the Space. Judges on one shared office network probably share one IP-based unauthenticated quota (not verified). Use a small or dynamic `duration` and make the CPU fallback the primary path for quota errors.
- The failover timing contradicts itself. The frontend 'tries A with a 20 s connect timeout, then B', while the same report says a sleeping Space takes 'about 1–2 min' to wake. On every cold start the frontend would give up on A and go to B, which may also be asleep, and then to the samples-only fallback. Branch on status_callback: for 'sleeping' or 'building', wait with a progress pill; fail over only on 'error' or 'stopped', or on a timeout after 'running'.
- The licence reasoning is inconsistent. YOLO26 (AGPL-3.0) is called 'fine for a public Space because the source is public', yet the report also recommends PRO 'protected' visibility (app public, source private) during development. AGPL §13 requires offering source to users of a network-served app, so a protected Space running AGPL weights conflicts with that reasoning.
- The rationale for gr.File over gr.Video is factually wrong. Gradio does not convert uploaded video unless `format` is set; conversion to playable MP4 is an output-side feature.
- Timeline colouring is undefined without a threshold. The report colours 'matched pairs' green, FPs red and FNs grey, and shows 'IoU with the matched GT' on hover. The spec defines matching separately for each τ ∈ {0.3, 0.5, 0.7} (greedy per class, pairs within a video, counts pooled). The same prediction can be a TP at τ=0.3 and an FP at τ=0.7. The Player needs a τ selector, or a status for each τ.
- Per-video Part B AP is ill-defined. The spec's AP is 'pooled across videos, chance-normalised' with r = pooled positive rate. For a sample with no accident there are no positive frames, so per-video AP is undefined, and per-video normalised AP does not equal the pooled figure. Show pooled AP for the dev set, plus per-video alarms and TTA. Also draw alarms that start inside ignored frames as discarded, since the spec discards them, so the risk-curve panel is 'correct' in the rubric's sense.
- The timestamp advice ('Use PTS-based t_sec; never frame index × fps') could conflict with the harness. RiskEstimator.step must use the t_sec that run_submission.py passes in. Part A times are 'seconds from first frame', and the GT carries an fps field. MP4s often have a non-zero first PTS (edit lists or B-frames), so raw PTS can shift every boundary. Once the starter kit arrives, check how run_submission.py and evaluate.py compute time and match that convention exactly (first PTS subtracted).
- The EDA-driven rule thresholds could break the spec's boundary conventions. 'Dwell ≥10 s → stopped_vehicle' and 'heading >120° for ≥1.5 s → wrong_way' are confirmation delays. The spec sets Start = 'vehicle stops' and Start = 'vehicle enters opposing lane', so starts must be moved back to the stop or lane-entry moment, or IoU@0.7 suffers. 'stopped_vehicle excludes queue zones' is spatial, but the spec condition is 'not in a queue at a signal': a vehicle stalled in the queue area with no queue would be missed. These rule cards should state the backdating explicitly.
- The demo latency table leaves out Part B. The report also runs RiskEstimator over every frame in the demo. Part B must be causal and may not reuse Part A output computed with future frames, and the official time budget covers A and B together (3× duration). The estimates are therefore optimistic, and the runtime figures in the report should cover A and B.
- Keep-alive: the evidence does not show that 2-minute pings caused the flag (the rule cited was 'Cloudflare'), and it does not show that a 6-hour cron is safe. A 48 h sleep would need at most a daily ping anyway. GitHub also disables scheduled workflows in public repos after 60 days without activity. On paid CPU Upgrade none of this is needed.
- Minor: Modal's '(up to 20 times)' is a browser redirect limit, not Modal's. Drawing a cross-origin video into a canvas does not break display; tainting only blocks reading pixels back, so the 'never draw the video into the canvas' reason is imprecise, though the advice itself is harmless.


## Missing points
- A zero-cost CPU Basic route: Gradio Spaces created before the July 2026 paywall still run (forum count: 249/250 up, 238 on CPU Basic). If any member has an old Space, reuse it for the demo backend; test on day 1 that pushing new code rebuilds on CPU Basic.
- A backend fallback on another platform. Space A and Space B both sit on Hugging Face, so an HF outage, a policy change or an abuse flag can take out both together. Keep a warm backup elsewhere, such as Modal or a team machine behind a Cloudflare Tunnel. On paid hardware, HF's native replicas beat a second account.
- Burned-in annotated MP4s for every sample, as a download and as a fallback in case the canvas overlay fails on a judge's phone or browser. The spec asks for 'annotated versions of every sample video rendered with own tooling'. A client-side-only overlay is a single point of failure for the 20% visualisation item.
- ZeroGPU constraints: only Python 3.10.13 and 3.12.12 are supported; the local machine runs 3.14, so pin python_version in the Space README. CUDA emulation at module level works only for PyTorch, so ONNX Runtime-GPU or TensorRT sessions cannot be created at import time.
- Pin versions to the current releases: Gradio 6.28.0 and @gradio/client 2.7.0 (both 18 Sep 2026). Keep the client and server majors compatible, and record the exact pins in the freeze tag.
- Before the demo renders anything, check its output with the same rules as the harness and evaluate.py --validate-only: labels from CLASSES, start < end, 0 ≤ start, end ≤ duration, no same-class overlaps, and end_sec = duration for events that run off the clip, including trimmed uploads. The 'events.json in the exact competition format' download should pass that check.
- GitHub Pages will not serve Git LFS videos (only pointer files) unless the Actions workflow checks out with lfs: true. Keep media out of LFS, or host it on an HF dataset repo or R2.
- Payment feasibility: HF PRO, CPU Upgrade and Modal overage need an international Visa/Mastercard. Cards from Uzbek banks may not work, so settle this on day 1 alongside account ages. ZeroGPU on a new account is unavailable until the account is 30 days old.
- The deadline is not in the PDF, but the 50–60 person-hour, 'Week 1–2' plan assumes one. Get the deadline from the organisers and cut the P1/P2 items to fit. Also allow for waiting on dev labels and for the lack of a local T4 (the GTX 1650 is 4 GB): runtime figures quoted 'on T4' must be measured on Kaggle, Colab or a cloud T4.
- Test that the site and the Space are reachable from the judges' likely networks (local ISPs and mobile data in Tashkent) and on phones. Also test the unauthenticated ZeroGPU path from a cold browser that is not logged in to HF.
- Be honest about the dev set on the Results and Report pages: the labels are the team's own, not the organisers', the sample count is small (high variance), and it is unknown which classes are absent from the samples. The rubric rewards 'failures stated plainly', and judges will compare site metrics with hidden-test behaviour.
