## Spec / logic errors
- Marginal-candidate section (§2.2) contradicts itself. It says 'a candidate that is surely real but passes only 1 of 3 τ … is net negative (ΔF1 −0.003 at P = 0.8)'. At P(real)=1 and F1_c=0.60 the report's own rule (credit 1/3 > F1/2 = 0.30) says emit, and ΔF1 = +0.003. The TL;DR 3 claim that IoU<0.5 segments 'often lower the score' and the advice to drop rather than emit poorly localised detections hold only when F1_c > 2/3·P(real). At the class F1 levels the report expects (0.3–0.6), surely-real IoU-0.3–0.5 detections should be emitted if they cannot be fixed.
- TL;DR 3 mechanism is misstated: 'because it counts as a false positive and still leaves the ground truth unmatched'. For IoU in [0.3,0.5) the segment is a TP at τ=0.3. The FP+FN double penalty applies only at the τ levels it fails.
- §1 table and key claim about clean_events: the report says the harness drops a segment 'if start ≥ end after clamping', which suggests output is always valid. The validity check runs BEFORE rounding to 3 dp, so a sub-millisecond event becomes [x, x]. evaluate.py then rejects the ENTIRE predictions.json ('Format check (runs first; any error -> exit code 1, nothing is scored)'). This is a catastrophic, cheap-to-avoid failure the report does not flag (verified with the official code).
- TL;DR 7 presents toy-simulation outputs as 'realistic regimes' ('AP is about 0.03–0.15 and mTTA/W about 0.03–0.08'). These values are set by the toy's parameters: 40 benign conflicts/h, precursors 1–5 s, 1–3-frame glitch spikes. The later 'illustration, not a performance forecast' caveat contradicts the TL;DR wording.
- TL;DR 8 / §3.2 prescriptions ('~0.2 s smoothing', 'no confirmation delays >0.2 s') rest on the toy glitch model (spikes of 1–3 frames, which a 0.2 s EMA exactly suppresses). The 'best in every setting' ranking is within one sd (FEW: 0.175±0.104 vs 0.166±0.095 vs 0.161). Real tracker failures (ID switches, multi-frame box jumps) could favour different settings.
- '~130 alarms/h' in §3.2 is really alarms per toy test set. It equals per hour only because the toy test set is 12×5 min = 1 h.
- TL;DR 8 is internally inconsistent: 'Keep a single alarm per conflict' vs 'cap alarm age at ~8 s' with a forced ≥2.1 s dip. The age cap creates a second alarm for the same conflict, and the first (unmatched) run becomes a false alarm, halving precision as the report's own §3.1 row shows (P=0.5).
- §2.5 'Attainable τ-mean F1 values … n = 1 gives {0, 0.5, 0.67, 1}' is wrong. Those are per-τ F1 values. τ-mean values also include 1/3, 2/9, 4/9, etc.
- §2.3 'worst-case IoU from quantisation' uses only boundary widening. Symmetric shrinking gives lower IoU (0.88 at stride 3 and 0.80 at stride 5 for 2 s events). 'Stride is a runtime decision, not an accuracy one' ignores stride's effect on tracking, contact detection and TTC.
- §4 equivalences ('Web live demo = 0.18 Score A', 'P1 Part A ≈45% of value') assume accidents are present in the test set. The code sets M = Score_A when there are none (evaluate.py line 350), so A's weight becomes 0.6 and Part B work is worth 0.
- Lipton et al. citation misspells the third author: Balakrishnan Narayanaswamy, not 'Naryanaswamy'.
- Minor: the §2.5 dev-set sd range '0.15–0.28 for 3–10 events' comes from a binomial approximation that conflicts with the report's own Monte Carlo (0.11–0.21).
- Minor: the report says the harness keeps 'the earlier-starting one' on same-class overlap. With equal start times it keeps whichever was listed first (stable sort on (label, start)), even if that one is shorter.


## Missing points
- Harness validity hole: events shorter than ~1 ms pass the harness check and become zero-length after rounding. evaluate.py then refuses the whole file. Enforce end − start ≥ 0.001 s (in practice the min-duration filter) and run --validate-only on every output.
- Where time is and isn't counted: solution.py is imported (load_solution) BEFORE any per-video timer, but sol.RiskEstimator() is constructed INSIDE each video's timed window. Load and warm up detector and tracker weights at module import, or in a module-level singleton reused across RiskEstimator instances, so neither Part B nor the first video pays model loading and CUDA init per video.
- Nothing preemptively kills a slow or hung detect_events. The over-budget verdict is applied after the fact, and a hang blocks all later videos. Part B's deadline is polled only every 100 frames. An internal wall-clock watchdog inside detect_events is therefore the only real protection.
- Explicit budget math is missing. Because Part B may not reuse Part A output (FAQ: 'reverse NOT allowed'), the detector and tracker effectively run twice per video: an offline Part A pass plus the harness-driven causal pass over every full-resolution frame decoded by cv2 on CPU. The samples include a 5.8 GB file (C3896.MP4), which suggests high bitrate or resolution. Split the 3× budget, e.g. ≤1.0–1.2× for A and ≤1.0–1.2× for B including decode, and benchmark cv2 decode on 8 cores early.
- Version-dependent behaviour: NumPy 2.4 needs Python ≥3.11, and the eval box only promises Python 3.10+. Pin Python and NumPy in requirements.txt or Docker so that dev (Python 3.14 / NumPy 2.4.2 locally) and eval behave the same, and always return float(x) or x.item() from step and in event tuples.
- Scenario where the test set has no accidents: Part B is then worth nothing and Score A carries 0.6 of the elimination score. Effort allocation should account for this (Part B is a bonus conditioned on accidents existing).
- Possible duration mismatch: the harness clamps event ends to CAP_PROP_FRAME_COUNT/fps, while validation compares against the GT 'duration' + 0.5 s. If organizers compute durations differently (e.g. PTS-based), an end at the metadata duration could fail validation. This is low probability, but worth clamping to a slightly shorter end or asking in the channel.
- The risk timestamps are nominal idx/fps, rounded to 4 dp, not container PTS. For non-integer fps (e.g. 29.97) or VFR sources, causal alarm timing relative to GT seconds could drift. It is worth checking once samples are available.
- No statistical treatment of the toy Part B ranking: paired differences between strategies, and confidence intervals on 'best' settings, are needed before prescribing specific smoothing constants.
