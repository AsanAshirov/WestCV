# Verification: verify:stack

Overall reliability: High on external facts, moderate on spec reasoning. Of 18 key claims, 12 are confirmed outright and 5 are partially correct. Kaggle's 30 GPU-h/week is unverifiable because the docs page did not render. Versions, dates, licences, latency tables, tracker defaults, TensorRT and NVDEC facts all check out against primary sources.

The partially correct claims:
- YOLO26 AP is the with-NMS column, although the report commits to NMS-free (e2e) inference.
- The ONNX Runtime move to CUDA 13 happened at 1.27, not 1.29. onnxruntime 1.24+ has no Python 3.10 wheels (1.25+ requires ≥3.11), which the report misses.
- The local decode benchmark is about 1.5x pessimistic, but its conclusion holds: converting frames to BGR costs more than decoding them.
- The OpenCV version needs pinning: PyPI is now at 5.x.
- YOLO12m is 52.5 AP at 4.86 ms, not ~51.9 at ~5.7.

The main problems are in reasoning:
- It treats Part B reusing Part A output as a "grey area", but the FAQ forbids it outright.
- It excludes signal queues from congestion, which the spec does not do.
- The emergency-brake argument is logically wrong.
- It overlooks Ultralytics' fuse_score and the stricter threshold for new tracks, so "stride 3 is acceptable in Part B" is doubtful for fast vehicles.
- It applies metric thresholds without any calibration step.
- Its advice on PyTorch CUDA 12 wheels is out of date.

The overall architecture is sound: YOLO26 plus ByteTrack, offline stitching in Part A, fixed-ROI traffic-light reading, and PyTorch FP16 as the default. It is usable once those corrections are applied.

## Spec / logic errors
- Part B reusing Part A output (§9): the report calls caching Part A detections or online tracker state into Part B 'arguably legal ... a grey area'. The spec FAQ is flat: 'Part A CAN use Part B's risk curve; reverse NOT allowed.' The Rules add: 'RiskEstimator.step uses only frames it has received; ... reusing Part A output that was computed with future frames, is a violation', and 'breaking a rule disqualifies'. Cached Part A detections of frame t were not computed from frames that step has received. Treat this as prohibited, not grey. (The report's fallback of keeping Part B self-sufficient is correct.)
- Congestion scope (§4): the report says signal state drives 'the exclusion of signal queues from stopped_vehicle and congestion'. Only stopped_vehicle has that exclusion in the spec ('not in a queue at a signal'). congestion is defined as 'traffic at a standstill or crawling across all lanes of a direction | Start: queue stops moving | End: queue clears', with no signal-queue exclusion. Excluding red-phase standstills from congestion is an unsupported assumption; settle it on dev labels or ask the organisers.
- Emergency brake (§5.5): 'If elapsed time exceeds 1.8× duration ... This only triggers in cases that would otherwise score zero' is logically false. The limit is 'Time per video (A + B) at most 3x'. With Part A at 1.8× and Part B at the report's own 0.2–0.5× (1080p), the total is 2.0–2.3×, well under 3×. The brake would therefore cut refinement in runs that would have scored. A wall-clock-dependent branch near its threshold can also make two runs differ, against 'two runs on same machine must give same predictions.json'. The threshold should be 3× minus the projected Part B cost minus a margin, and it should be logged.
- Tracker thresholds (§3.3) and stride advice (§3.2): 'match_thresh 0.8 (IoU ≥ 0.2)' ignores Ultralytics' default fuse_score=True, under which the condition is IoU×score ≥ 0.2. Newborn (unconfirmed) tracks need IoU×score ≥ 0.3 (hard-coded 0.7 cost), matched against a zero-velocity prediction. With the report's own IoU table, a 60 km/h car at stride 3 has raw IoU 0.38; at a typical score of 0.6 that gives 0.23 < 0.3. The newborn track is deleted and re-spawned every processed frame and never confirmed. So 'Stride 3 is acceptable in Part B' contradicts the report's own analysis, and Part B depends on tracks of fast vehicles for TTC. Either keep stride ≤ 2 for Part B at 1080p, set fuse_score False, or use the `trackers` library with frame_rate scaling and verify on dev clips.
- Collision-start rule (§7): requiring 'both vehicles stationary afterwards' conflicts with the accident definition. The spec says 'contact between two+ road users, or road user and fixed object' and 'End: all involved objects stop moving or leave the frame'. Glancing collisions where vehicles drive on or leave the frame would be missed. So would single-vehicle crashes into a fixed object, where there is only one track and no second footprint.
- Metric thresholds without calibration: the report uses physical units throughout: 1.5 m stitch radius, 8 m/s², |Δv| > 3 m/s, queue speed < 1 m/s, footprint distance < 1 m, and the IoU table in metres. It gives no procedure for getting a metric ground-plane homography. The spec itself notes speeding is excluded because it 'cannot be measured without calibration'. Without a calibration step (e.g. from lane widths or dash lengths in camera.md), these thresholds are undefined.
- Timestamps (§9): 'Use container PTS minus the first PTS, so times ... match the harness's t_sec' is stated as fact. The spec only says 't_sec = frame timestamp' and 'seconds from first frame'. The harness may compute t_sec as frame_index/fps. Check run_submission.py before relying on this; the two agree for CFR 25 fps but diverge on VFR files.
- YOLO26 accuracy (§1.1/§1.3): the report quotes the with-NMS mAP (40.9/48.6/53.1/...) while committing to NMS-free end-to-end inference, whose documented mAP is 40.1/47.8/52.5/54.4/56.9. The RF-DETR-S vs YOLO26s comparison is therefore 53.0 vs 47.8, not 48.6.
- Dev GPU (§8): 'GTX 1650 is sm_75 (the same architecture as the T4, so kernels are identical) but it has no tensor cores' contradicts itself. Without tensor cores, cuDNN/cuBLAS pick different FP16 kernels than on a T4, so neither numerics nor timings carry over. The conclusion to benchmark on a T4 is right.
- ROI crop (§5.4): cropping to the carriageway bounding rectangle before detection can remove pedestrians on the kerb before they step onto the road, and objects near the edges. The jaywalking start is 'pedestrian steps onto road', and failure_to_yield counts a pedestrian 'stepping onto' the crossing. Keep a margin around crossings and kerbs in the crop.
- Driver and wheel advice (§6): 'CUDA 12.x wheels (cu126/cu128)'. torch 2.14 has no cu128 build (the newest cu128 wheel is torch 2.11), cu126 is 'Legacy' in 2.14 and proposed for removal in 2.15, and default PyPI torch 2.14 is CUDA 13.2. A bare --extra-index-url without pinning the local version (torch==2.14.0+cu126) is fragile; --index-url is the documented route.
- ONNX Runtime (§6 table): 'onnxruntime-gpu ≥ 1.29 → CUDA 13'. The CUDA 13 default started at 1.27. More importantly, onnxruntime ≥1.25 requires Python ≥3.11, so the recommended ONNX-CPU fallback would not install on the promised 'Python 3.10+' baseline unless pinned to ≤1.23.2.


## Missing points
- A concrete ground-plane calibration step: a homography from camera.md and lane markings (standard lane width, dash length), validated on sample tracks. Every metric threshold, the TTC signal and the footprint-contact rule depend on it.
- Clean-machine dependency traps beyond PyAV. torchcodec needs a system FFmpeg 4–9 and has CPU-only wheels on Windows. On Python 3.10: onnxruntime ≤1.23.2, numpy ≤2.2.6, scipy ≤1.15.3. opencv-python on PyPI is now 5.0.x vs local 4.13, so pin it. opencv-python (non-headless, pulled in by ultralytics) needs libGL in slim Docker images. Set YOLO_AUTOINSTALL=False/YOLO_OFFLINE so missing deps fail loudly. Produce a lock file for Python 3.10 and one for 3.12, and test both in `docker run --network none`.
- Ultralytics tracker internals that matter at stride > 1: fuse_score, the hard-coded 0.7 unconfirmed-track cost, and zero-velocity birth. Also resetting tracker state between videos in Part A (a new tracker per detect_events call; do not use persist=True across videos).
- Any concrete guidance for night/IR, rain, glare and motion blur on detector recall beyond 10% grayscale augmentation. For example, measure per-lighting recall on the held-out sample video, and set a lower confidence floor or larger input at night.
- TensorRT kSAME_COMPUTE_CAPABILITY and version-compatible engines, as a middle ground if speed is ever short. Also the caveat that 'T4-class' may not be sm_75 at all.
- AGPL §13 detail for the live demo: the backend code serving the model must itself be published, e.g. in the same repo. A link to a repo that lacks the demo server code does not satisfy it.
- GPU memory and startup cost of keeping all models loaded in one process: Part A YOLO26m, optional seg, D-Fire YOLO26n, YOLOE-26, plus the Part B model. Include CUDA context and warm-up time in the per-video budget, since the harness is sequential and video 1 may pay the load cost.
- A detector-level dev metric tied to the rules: small-object recall at the far field and the ID-switch rate on hand-labelled clips. Hand-corrected detection frames alone do not measure tracking quality, and tracking quality drives the IoU-0.7 boundaries.
- The run order: detect_events is called before Part B streams frames. So Part A cannot consume the harness's Part B risk curve unless Part A instantiates its own RiskEstimator internally (allowed by the FAQ). This affects the plan to share TTC logic.
