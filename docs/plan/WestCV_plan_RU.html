1.Главное на одной странице

  1. Главный риск — не качество модели, а запуск и время. Если пакет не запустился, модельная оценка M обнуляется: в типичном сценарии это −0.26 отбора (26 баллов из 100). Для сравнения, всё live-демо стоит 7.5 балла.
  2. Сэмплы тяжелее, чем обещает PDF: 3840×2160, 29.97p (в PDF — «25 fps»), H.264 High 4:2:2 10-bit, ~140 Мбит/с. Один только проход харнесса cv2.read() для Part B занимает 0.84–1.0× длительности на 8 vCPU под Linux и ≈1.4–2.1× на AWS g4dn.2xlarge (оценка). Лимит — 3× на Part A и Part B вместе. NVDEC на T4 этот формат не декодирует.
  3. Один закон бюджета: T_A = 3·dur − 1.2·(Part B вместе с декодом харнесса) − 0.2·dur. План строится из meta и таблицы стоимостей, измеренной на T4; настенные часы — только аварийный тормоз. Модели грузим и прогреваем при импорте solution.py — это время в бюджет видео не входит.
  4. Score A — macro-F1 по множеству C = (классы GT) ∪ (наши классы). Класс, которого нет в тесте, но который мы хоть раз предсказали, добавляет в среднее ноль. Предсказываем класс, только если p·f > (1−p)·q·S̄. Стартовый набор: stopped_vehicle, jaywalking, wrong_way, congestion, accident.
  5. F1 при tIoU 0.7 определяется точностью границ. Допустимый сдвиг для события 2 с — 0.35 с, для 5 с — 0.88 с. Границы привязываем к геометрическим моментам (касание, пересечение стоп-линии, вход в полигон), а для классов с окном подтверждения переносим старт назад.
  6. Постобработка стоит больше, чем подбор моделей: интервалы по трекам → объединение → склейка разрывов → минимальная длительность → санитайзер (длина ≥ 0.05 с, округление до 3 знаков, конец ≤ floor(duration, 3)). Событие короче 1 мс после округления заставит evaluate.py отвергнуть весь файл.
  7. Архитектура Part A: единый CPU-декод → YOLO26m (дообученный на наших кадрах) → ByteTrack → следы в метрах через гомографию → модули правил на геометрии scene.yaml → уточнение границ → постобработка. Обучаются детектор, детектор огня и дыма и (опционально) кроп-верификатор аварий; всё остальное — правила.
  8. accident и near_miss строятся на парной кинематике: зазор между следами, TTC/PET, Δv за 1 с, hinge-fit момента начала. Верификатор X3D или VideoMAEv2 только подтверждает кандидата и никогда не задаёт границы. VLM по умолчанию выключен.
  9. Part B весит 18 баллов, но только если в тесте есть аварии. Собственная причинная перцепция, никаких выходов Part A. Сигнал двухканальный: ранжирующий канал ≤ 0.4999, тревога ≥ 0.5 только при уверенном неизбежном конфликте. Тревоги короткие (≤ 8 с), бюджет ложных — ≤ 1.8 в час.
  10. Разметка: Label Studio (TimelineLabels, frameRate = 29.97002997) на 1080p-прокси, где сохранён каждый кадр. Каждый сэмпл размечают двое независимо, согласие меряем официальным evaluate.py (цель F1 ≥ 0.8 при τ = 0.5). Боксы — X-AnyLabeling, геометрия — labelme.
  11. Датасеты: ACCIDENT, TAD, AI City 2021 Track 4, UA-DETRAC, D-Fire, RAOD, MIO-TCD, CADP, плюс COCO и Street Scene. До обучения нужно решить развилку «веса Ultralytics под AGPL-3.0 против данных под NC-SA».
  12. Сайт даёт 25% отбора, одно live-демо — 7.5 балла (эквивалент +0.18 к Score A). Статический сайт на GitHub Pages плюс Gradio-бэкенд на HF Space.
  13. Порядок работ: сначала рабочая сдача, потом улучшения. D0 — сэмплы, прокси, бенчмарк декодирования, тег v0.1. Вопросы организаторам (раздел 10) отправить сразу: главные — формат тестовых видео, CPU оценочной машины, дедлайн.

2.Задача и как её оценивают

Фиксированная CCTV-камера смотрит на дорогу. Для каждого .mp4 нужно:

  • Part A (обязательно) — вернуть все события как список [start_sec, end_sec, label] по 14 официальным классам. Видео можно читать как угодно: несколько проходов, произвольный доступ, взгляд в будущее.
  • Part B (бонус) — на каждом кадре вернуть вероятность того, что авария начнётся в ближайшие 5 с, используя только уже полученные кадры.

2.2Формулы оценки и цена каждой составляющей

Score A = (1/|C|) · Σc∈C (1/3) · Στ∈{0.3, 0.5, 0.7} F1c(τ), C = классы GT ∪ классы наших предсказаний
Score B = 0.4·AP + 0.4·F1alarm + 0.2·min(1, mTTA / W), H = 5 с, W = 10 с, θ = 0.5
M = 0.7·Score A + 0.3·Score B (M = Score A, если в тесте нет аварий)
Отбор = 0.6·M + 0.25·Website + 0.15·Code = 0.42·A + 0.18·B + 0.25·Web + 0.15·Code

Сопоставление в Score A: для каждого класса и τ считается temporal IoU всех пар «GT–предсказание» одного видео, пары сопоставляются жадно по убыванию IoU (пара засчитывается, если IoU ≥ τ и оба сегмента свободны). TP, FP и FN суммируются по всем видео, потом считается F1. Векторизованная копия нашего скорера совпала с официальным Score B с точностью 2.2·10−16 на 40 случайных случаях.

2.4Как харнесс обрабатывает видео (по коду)

импорт solution.py (load_solution): загрузка моделей — ДО любых таймеров, не тарифицируется
для каждого видео по очереди:
  t0 = perf_counter();  budget = 3 * CAP_PROP_FRAME_COUNT / CAP_PROP_FPS
  events = detect_events(path)                 # Part A; читает файл как угодно; никто её не прерывает
  если Part A уже вышла за бюджет  -> Part B пропускается
  est = sol.RiskEstimator(); est.reset(meta)   # новый объект на каждое видео, уже внутри таймера
  cv2.VideoCapture(path): read() КАЖДОГО кадра -> step(frame, idx/fps)   # дедлайн проверяется раз в 100 кадров
  если total > budget            -> events = [], risk = []   (Part A тоже теряется!)
  исключение в detect_events     -> events = []
  исключение внутри step         -> risk = [] для всего видео, events сохраняются
  step вернул не скаляр / None   -> 0.0 для этого кадра;  NaN -> 0

Размывание: когда вообще предсказывать класс

Обозначим: p — вероятность, что класс есть в тесте; f — ожидаемый F1 на нём; q — вероятность хотя бы одного ложного срабатывания на всём тесте, если класса нет; S̄ — средний F1 остальных N классов. Если класс есть, он попадает в C при любом нашем решении, и предсказание даёт +f/(N+1). Если класса нет, одно ложное срабатывание добавляет в C класс с нулём и отнимает S̄/(N+1) — ровно столько же, сколько сто ложных. Проверено на официальном скорере: 0.5556 → 0.4167 при одном ложном fire_smoke и столько же при трёх.

Предсказывать класс, если p·f > (1−p)·q·S̄. Порог: p* = q·S̄ / (f + q·S̄). Перевод FP/ч в q: q = 1 − exp(−λ·T), T ≈ 0.28 ч

3.4Метрика Part B: механика и ловушки

Разметка кадров (порядок проверок в frame_label): кадр внутри аварии [s, e] → игнор; иначе кадр в [s−5, s) → позитив (сильнее игнора near-miss); иначе кадр в [snm−5, enm] вокруг near_miss → игнор; всё остальное — негатив. AP — пошаговая (как в sklearn) по кадрам всех видео, нормированная: AP = max(0, (APraw − r)/(1 − r)). Тревога — максимальная серия кадров со скором ≥ 0.5; серии с разрывом < 2 с сливаются до отбрасывания тревог, начавшихся на игнорируемых кадрах. Каждой аварии сопоставляется самая ранняя свободная тревога с началом в [s−10, s); остальные ложные. F1alarm = 2m/(A + N); TTA = s − начало тревоги.

Ловушки
  1. Опоздание смертельно: тревога, начавшаяся в момент контакта или позже, попадает на игнор и выбрасывается. Цель — старт за ≥ 0.5–1 с до контакта.
  2. Слияние с ранней ложной тревогой (< 2 с) переносит начало раньше; если раньше s−10 — совпадения нет.
  3. Слияние с серией, начавшейся на игноре (внутри аварии или окна near-miss): слитая тревога получает игнорируемое начало и выбрасывается целиком.
  4. Длинные тревоги не работают; вторая тревога перед той же аварией — ложная; высокие скоры после e — негативы для AP.
Оптимальная форма сигнала
  1. Два канала: ранжирующий ≤ 0.4999 всегда, тревожный ≥ 0.5 только при уверенном неизбежном конфликте.
  2. Монотонность по неизбежности (падению TTC); физические шкалы, без нормировки по видео.
  3. Лёгкое сглаживание (~0.2 с), без задержек подтверждения.
  4. Сброс после контакта, подавление пары ≤ 10 с; цепные аварии не глушить.
  5. Возраст тревоги ≤ 8 с без принудительного повторного включения.
  6. Порог 0.5 — по бюджету ложных тревог: ≤ 0.5 на тест ≈ ≤ 1.8/ч на сэмплах вне окон near-miss. mTTA не гнаться: 0.3 → 2 с даёт лишь ≈ +0.03.

F1alarm при малом числе аварий (recall 0.6): 1 авария — 0.75 без ложных, 0.46 при одной ложной, 0.33 при двух; 3 аварии — 0.75 / 0.62 / 0.53; 10 аварий — 0.75 / 0.71 / 0.67. Каждая ложная тревога при 1–3 авариях стоит 0.05–0.3 F1. При малом числе аварий разброс Score B ≈ 0.1, поэтому Part B ограничиваем ≈ одной человеко-неделей.

4.Архитектура решения

Part A работает офлайн: может смотреть в будущее, делать несколько проходов и обращаться к файлу в любом порядке. Part B строго причинный и не использует никаких выходов Part A; общими могут быть только веса и код. Подход гибридный: обучаемые модели дают восприятие (детекция объектов, огонь и дым, подтверждение аварий), а решения о событиях принимают правила на траекториях в метрах и на геометрии сцены. Так границы событий привязаны к физическим моментам, а поведение объяснимо и настраивается на малом dev-наборе.

4.1Общая схема Part A

Ключевые принципы

  1. Одно декодирование на Part A. Все потребители кадров берут их из одного последовательного прохода. При 4K любое повторное чтение окон стоит 0.4–0.5× длительности и больше, поэтому окна уточнения собираем из кольцевого буфера во время основного прохода. Произвольный доступ PyAV — только для 1080p или при явном запасе.
  2. Кэш для разработки: детекции и треки каждого сэмпла сохраняются в .npz с ключом «хэш видео + хэш конфига». Перезапуск правил занимает секунды, и пороги подбираются против dev-разметки через evaluate.py. В сабмишене кэш не используется.
  3. Part A не создаёт RiskEstimator внутри себя: это повторно оплатило бы декод (0.5–1.3× при 4K). Те же TTC-признаки Part A считает по своим трекам почти бесплатно (≈0.005×). FAQ разрешает Part A использовать кривую риска, обратное — нет.
  4. Хуки для сайта сразу: detect_events(path, fast=False, on_progress=None); треки, зоны и track_ids сохраняются для каждого события, чтобы рисовать их в плеере.

  1. План строится только из meta (fps, width, height, n_frames) и таблицы стоимостей, измеренной на T4 и похожем CPU. Из плана выводятся stride, размер входа, число окон уточнения и включённые опции. Такой план детерминирован.
  2. Этапы Part A упорядочены по ценности: детекция и трекинг → правила → уточнение границ → тайлинг → верификаторы. При отсечке первыми выпадают уточнение, тайлы и VLM.
  3. Аварийная проверка: в начале detect_events читаем 60 кадров так же, как харнесс, и получаем h — стоимость харнесса в долях длительности (2–4 с). Если h больше табличного более чем на 30% — берём уровень легче и логируем. Уровень можно зафиксировать переменной WIUT_TIER.
  4. Защита Part B: каждые 32 вызова step() прогнозирует now + оставшиеся_кадры × EMA(dt); если прогноз выходит за «дедлайн − 5 с», stride удваивается. Таймаут обнуляет обе части, поэтому это важнее качества.
  5. Всё тяжёлое — при импорте: загрузка моделей, контекст CUDA, cuDNN, прогревы. В step() не копировать 4K-кадр (9 мс): сразу cv2.resize в заранее выделенный буфер (1–2 мс).
  6. Part B с фиксированным лагом L = 3: рабочий поток считает детектор, трекер и TTC для кадра t, вызов step(t + L·stride) ждёт результата. Решение остаётся причинным и детерминированным, GPU перекрывается с декодом харнесса; цена — 0.1–0.3 с TTA.

Ловушки трекеров
  • fuse_score. В Ultralytics по умолчанию fuse_score=True: условие первого этапа — IoU × score ≥ 0.2, новорождённые треки проходят только при IoU × score ≥ 0.3 и предсказываются с нулевой скоростью. Машина на 60 км/ч при stride 3 даёт сырой IoU ≈0.38; при score 0.6 это 0.23 < 0.3 — трек не подтверждается. Stride 3 при 29.97 fps допустим только с fuse_score=False, либо с trackers (там IoU не умножается на score), либо с пониженным порогом рождения.
  • Буферы считаются по-разному: Ultralytics — max_frames_lost = track_buffer в обработанных обновлениях без масштабирования по fps; FoundationVision и trackers — frame_rate/30 · track_buffer. Решение — один модуль tracker_config.py, буферы задаются в секундах. Пример: 3 с при 29.97/stride 2 (15 Гц) — это 45 обновлений в Ultralytics и track_buffer = 90 при frame_rate = 15 в trackers.

Офлайн-ремонт треков (только Part A)

  • Движущиеся объекты: зазор ≤ 2–4 с; |pA + vA·Δt − pB| ≤ 2 м + 0.5·|v|·Δt; тот же суперкласс; отношение площадей в [0.5, 2]; опционально сходство HSV-гистограмм; решение — венгерский алгоритм.
  • Стоящие объекты: зазор ≤ 30 с при совпадении положения в пределах ≈1.5 м, плюс «ghost-боксы»: потерянный стоящий трек живёт, пока ≥ 40% его бокса статично или ≥ 60% остаётся передним планом долгого фона.
  • Разрез по неправдоподобным скачкам (ускорение > 8 м/с², поворот курса > 90° за 0.2 с) вне окон кандидатов в аварию: разрезать безопаснее, чем склеивать.
  • Сглаживание: фильтр Хампеля → интерполяция разрывов ≤ 1 с → Savitzky–Golay (порядок 2) или RTS.
  • Переключения ID порождают ложные wrong_way, illegal_u_turn, solid_line_crossing, поэтому в «подозрительном окне» правила с разворотом курса и скачками Δv не срабатывают.

4.6Общие библиотеки: следы, полосы, кинематика, конфликты

След на земле

  • Нижняя середина бокса — ближайшая к камере точка следа.
  • Ориентированный прямоугольник по классу (оценка): car 4.5×1.8 м, van 5.5×2.0, truck 8–9×2.5, bus 12×2.5, motorcycle 2.0×0.8, bicycle 1.8×0.6, пешеход — диск 0.5 м.
  • Из него — передняя и задняя точки для red_light, stop_line, failure_to_yield: ошибка положения переда в 4.5 м при 15 м/с — это 0.3 с, весь допуск IoU 0.7 для 2-секундного события.
  • Поправка на высокие машины: для полосы вычитаем медианное боковое смещение точек контакта (для solid_line_crossing обязательно).
  • Флаги надёжности: бокс у края кадра (≤ 3 px) — обрезан; бокс перекрыт ближним — вес ниже.

Полосы с гистерезисом

Новая полоса фиксируется, если держится ≥ 0.5 с и центр отошёл от разделителя на ≥ 0.5 м. Пересечение разделителя — смена знака расстояния с |d| ≥ 0.3 м по обе стороны не менее 0.4 с.

Кинематика (одна библиотека на всех)

  • Part A: Хампель → RTS или центрированный SG. Part B: Калман с постоянной скоростью.
  • Курс — только при скорости > 1 м/с, иначе держим последний.
  • Состояния: стоит — < 0.5 м/с и смещение < 1 м за 2 с; ползёт — < 2 м/с; едет — > 3 м/с.
  • Резкое торможение: Δv за 1 с ≤ −3 м/с при vдо ≥ 4 м/с. Момент начала офлайн — hinge-fit (двухсегментная кусочно-линейная v(t)). Мгновенное ускорение не пороговать: после SG(1.5 с) реальное торможение 0.5 с не доходит до −3.4 м/с²; onset по SG смещён раньше на ≈−0.25 с — вычитаем как известную поправку.

Модуль конфликтов (accident, near_miss, Part B)

  • TTC: постоянная скорость; первый момент τ ∈ [0, 5] с (шаг 0.1 с), когда капсулы следов (+0.3 м) пересекаются.
  • Согласованность TTC: доля последних 0.8 с, где TTC падал ≈ на 1 с/с — главный фильтр против следования в потоке.
  • PET, T2, DRAC = Δv²/(2·зазор), скорость сближения, dmin; MTTC — только попутные пары.
  • Стартовые пороги: TTC ≤ 1.5 с (SSAM) или PET ≤ 1.5 с; DRAC 3.35 м/с² (Archer 2005).
  • Опоры, отбойники, островки — неподвижные капсулы (удар об объект).
  • Готовый код: Two-Dimensional-TTC и SSMsOnPlane (MIT) — 2D TTC по ориентированным прямоугольникам, ≈0.036 с на 10⁴ пар.

Поле направлений: сетка по плоскости земли (1 м) или изображению (64 px) — гистограмма курсов и доминирующее направление по всем трекам. Проверяет нарисованные вручную направления полос и служит запасным путём для wrong_way. Атлас нормальности: по ячейкам — направления, скорости и вероятность остановки; остановка там, где никто не останавливается, — сильный признак аварии или stopped_vehicle.

4.7Светофор, огонь и дым, препятствия

Светофор [camera.md]

  1. ROI каждой лампы в scene.yaml (центр и радиус) переносится регистрацией, затем локальный NCC-поиск шаблона корпуса ±40 px в 4K. Лампа ≈20 px в 4K — самый хрупкий элемент сцены.
  2. Признаки: 90-й перцентиль V в диске лампы, медианная S в кольце, циркулярная медиана оттенка по насыщенным пикселям.
  3. Калибровка по видео: Part A — 2-means по V за всё видео даёт порог «горит / не горит»; Part B — пороги с сэмплов плюс скользящая история.
  4. Положение важнее цвета: горящая лампа — argmax яркости относительно её базового уровня, оттенок только подтверждает (переживает сдвиг баланса белого на закате).
  5. Мерцание LED: берём максимум по окну из 3–5 отсчётов и сдвигаем переходы назад на w/2.
  6. Фаза: HMM + Viterbi с минимальными длительностями (Part A), гистерезис (Part B). Красный+жёлтый трактуем как красный [орг.]; при блике — «неизвестно», держим предыдущее. Фиксированный цикл не предполагаем (в Ташкенте есть табло отсчёта и адаптивное управление).
  7. Если сигнал не виден — фаза из поведения потока: очередь у стоп-линии и пересечения за 5 с; начало зелёного ≈ отъезд головы очереди минус 1–1.5 с. Правила, зависящие от красного, тогда работают только в режиме высокой точности. Запасной классификатор на кропах — Autoware traffic_light_classifier (MobileNetV2, ONNX, Apache-2.0).

Огонь и дым (fire_smoke)

  • YOLO26n/s, дообученный на D-Fire (21 527 изображений, CC0) + 10–15% кадров-негативов сцены (стоп-сигналы, красные машины, блики, пыль, выхлоп); 1–2 Гц. Обучение ≈1–2 ч на Kaggle T4.
  • Подтверждение: присутствие в 7 из 10 отсчётов за 5 с (уверенность: дым 0.35, огонь 0.45); на дороге или на машине, не на небе, ≤ 25% кадра; не привязан к машине, едущей быстрее 2 м/с дольше 3 с; огонь — мерцание 3–12 Гц, вариация площади CV ≥ 0.1, R > G > B; дым — нежёсткий поток вверх.
  • Старт — перенос назад по трассе детектора с порогом 0.15. По умолчанию выключен.

Препятствия (road_obstacle)

  • (а) Животные COCO (классы 15–19, уверенность ≥ 0.4, ступни на проезжей части ≥ 1 с) — за тем же аудитом ложных.
  • (б) Статичный блоб двойного фона: 0.05–6 м², ≥ 70% внутри проезжей части, ≥ 3–5 с, не объясняется боксами (IoU < 0.1 для ≥ 80% времени), текстурный тест против теней, верификатор YOLOE-26 с «запечённым» словарём или OWLv2 на кропе.
  • Долгий фон замораживается до появления объекта, иначе объект «впитается». MOG2 поглощает остановку за T ≈ 0.105/(α·f) с, только если передавать learningRate=α в каждый apply(). По умолчанию выключен.

4.8Аварии и near-miss: кинематика + верификатор

Организаторы прямо пишут, что обученные модели полезнее всего для этих двух классов. Но сегмент аварии (от первого контакта до остановки всех участников) длится ≈2–6 с (оценка), и для IoU 0.7 суммарный сдвиг границ должен быть ≤ 0.18·L: ≈0.35 с для 2-секундного события. Такую точность даёт только траектория, поэтому ядро — кинематика, а обучаемая модель только подтверждает.

(а) Кинематические признаки (ядро)

  1. Контакт: зазор между прямоугольниками следов ≤ 0.5 м при скорости сближения ≥ 1.5 м/с за предыдущую секунду; защита от перекрытия в кадре (нижние кромки согласованы по глубине, |Δybottom| ≤ 0.15·h).
  2. Шок в [−0.3, +0.8] с от контакта: Δv за 1 с ≤ −max(2.5 м/с, 0.35·vдо); или поворот курса ≥ 25° за 0.5 с при v ≥ 3 м/с вне зон поворота; или боковой скачок ≥ 0.8 м; или стоявший участник внезапно смещается.
  3. После удара: участники стоят (< 0.5 м/с) ≥ 2–3 с вне обычных зон остановки и не в очереди.
  4. Уязвимые: h/w бокса пешехода или двухколёсника падает на > 40% за 0.5 с; райдер отделяется; трек человека обрывается под машиной.
  5. Один против объекта: Δv ≥ 5 м/с за ≤ 0.5 с у края дороги, опоры или островка, без других участников в 3 м.
  6. Патология треков: обрыв вдали от края кадра или слияние двух ID в один блоб в пределах 2 с от сигналов 1–2.

Границы. START — первый кадр с зазором ≤ 0.2 м (или контактом масок) в окне [tc − 1, tc + 0.5] после повторного трекинга на полной частоте; если геометрия ненадёжна — tшок − 0.1 с. END = maxi min(tstop,i, texit,i) (формула «min(все остановились, последний уехал)» неверна при смешанных исходах). Цепная авария — один сегмент (склейка < 1 с), min 1.0 с, предохранитель ≤ 3 аварий на видео при p < 0.9.

4.10Постобработка сегментов

1. интервалы по каждому объекту→2. уточнение границ (геометрия, субкадровая интерполяция, перенос начала назад)→3. малая калибровка смещения по классу (медиана pred − GT на dev)→4. union перекрывающихся и касающихся→5. gap-merge→6. min_dur / max_dur→7. гейтинг класса и порог→8. санитайзер

Санитайзер (последний шаг, покрыт юнит-тестами)

  1. метка из CLASSES;
  2. Python float, отбросить NaN и бесконечности;
  3. start = max(0, start);
  4. end − start ≥ max(min_dur_c, 0.05);
  5. округлить до 3 знаков;
  6. end = min(end, floor(duration, 3)), duration = CAP_PROP_FRAME_COUNT/fps;
  7. повторно проверить start < end;
  8. объединить перекрытия одного класса; отсортировать.

Событие за концом видео получает end = duration, событие с первого кадра — start = 0.

Общие правила из PDF и FAQ
  • Одно событие — один непрерывный сегмент одного класса. Два одновременных события разных классов — две записи (встречка, вызвавшая аварию, — это wrong_way + accident).
  • Сегменты одного класса не должны перекрываться. Если два события одного класса происходят одновременно, их выдают одним сегментом, покрывающим оба; организаторы размечают так же.

  • Превышения скорости в списке нет: без калибровки его не измерить. Все 14 классов официальные, любой может быть в тесте, и в тесте есть события, которых нет в сэмплах.

in_signal_queue: машина в зоне очереди подхода, фаза красная/жёлтая (или < 8 с с начала зелёного), и она у стоп-линии (< 3 м) или за стоящей машиной из очереди. Старт — момент остановки, а не +10 с: GT [0, 25] против выдачи [10, 25] даёт IoU 0.6 и провал при τ = 0.7. После аварии stopped_vehicle выдаём (классы могут перекрываться). Автобусы на остановке и такси — по буквальному определению, парковочные карманы исключаются [орг.]. Защита от автоэкспозиции: если > 40% дороги меняется за 1 с — переинициализировать фон и заглушить статичные события на 10 с.

jaywalking

Вход: ступни внутри дороги на d ≥ max(0.4 м, 0.1·рост) в течение 0.6 с; выход: d < 0 в течение 0.6 с; затем границы переносятся назад к пересечениям нуля (иначе старт опаздывает почти на 1 с). Min 1–1.2 с, склейка ≤ 1 с. Спорно [орг.]: люди, выходящие из машины, полиция, дорожные рабочие. Перекрёсток целиком не исключать: там бывает диагональное пересечение.

congestion: две гипотезы

H1 (по умолчанию): очередь у сигнала засчитывается, только если она не рассасывается на зелёном ≥ 10 с, или доходит до края зоны или в перекрёсток, или длится > 1.5× самого длинного красного из EDA (без сигнала — 45 с). H2 (переключатель): любая остановка всех полос ≥ 20 с. Dev размечаем в обоих вариантах [орг.]. Min 20–30 с, склейка 10–15 с.

wrong_way

Задний ход и парковку отсекают условия «скорость ≤ 2 м/с и путь < 8 м». На дуге разворота выравнивание ≈0, поэтому класс срабатывает, только если машина продолжает ехать по встречной. Сочетания: обгон через сплошную = solid_line_crossing + wrong_way; поворот на одностороннюю навстречу = illegal_turn + wrong_way.

red_light против stop_line

Машина, заехавшая за линию на красный и остановившаяся до перекрёстка, — по умолчанию только stop_line [орг.]. Если фаза выводится из потока, дополнительно требуем ≥ 2 пересечений на конфликтующем подходе за ±3 с и стоящую собственную очередь. Проезд на жёлтый — не red_light: метки ставим по определениям задания, а не по ПДД.

Синтетические тесты траекторий

Для каждого класса вручную заданный трек в координатах плоскости земли должен давать ровно один сегмент с ожидаемыми границами. Это единственная проверка для классов, которых нет в сэмплах.

6.2Подготовка видео: прокси с сохранением кадров

Браузеры, Windows Media Foundation и JavaFX оригиналы 4:2:2 10-bit не воспроизводят (Chrome и Edge играют программно, но в 4K теряют кадры, а переход занимает 0.5–3.2 с). Поэтому все браузерные и десктопные плееры работают с прокси, в котором сохранён каждый кадр и частота 29.97. Проверено на синтетике 3840×2160 yuv422p10le 30000/1001: 120 пакетов на входе и выходе, start_time 0, длительности совпадают.

Шаг 0. Сравнить длительности аудио и видео в каждом файле (Label Studio предупреждает, что разные длительности дают лишние кадры). Если аудио отличается — заменить аудио-часть команды на -an.

ffprobe -v error -show_entries stream=index,codec_type,duration -show_entries format=duration -of compact=p=0 C3896.MP4

Чего никогда не делать
  • Не добавлять -r, фильтр fps= или -ss перед -i — меняется число кадров. Команду из документации Label Studio с -r 30 не копировать.
  • Не выставлять цветовые теги вручную: принудительный bt709 сдвигает BGR в OpenCV в среднем на 6.5–11.8 уровня.
  • Ловушка drawtext: %{pts:flt:3} добавляет смещение 3 с, а не задаёт точность.
  • Цветовые пороги (лампы светофора) настраивать на кадрах, декодированных как в харнессе, а не на прокси.

6.5Гайдлайн по границам

Файл docs/annotation_guide.md: конвенции начала и конца дословно из PDF, командные уточнения и лист примеров. Единообразие конвенции важнее точности до одного кадра. Если организаторы опубликуют уточнения или примеры GT, они важнее всего, что ниже.

  • Кадры и секунды. Время считаем по оригиналу. start — первый кадр, на котором определяющее условие видно выполненным; end — последний кадр, на котором оно ещё выполнено (включительно). Конвертер пишет start_sec = f_start/fps, end_sec = (f_end + 1)/fps.
  • Допуск скорера: при сдвиге δ IoU = (L − δ)/(L + δ); для IoU ≥ 0.7 нужно δ ≤ 0.18·L: у события 3 с это ≈16 кадров, у события 1 с — только ≈5. Больше всего внимания — коротким классам: near_miss, red_light, solid_line_crossing.
  • Одно событие = один участник (или одна взаимодействующая пара) и один класс. Две машины, проехавшие на один красный, — два события на уровне разметки, но в GT одновременные события одного класса сливаются в один сегмент (FAQ). Тот же участник и класс с разрывом < 1 с — одно событие.
  • Ставим все подходящие классы, перекрытия — норма: например, accident → stopped_vehicle (если ≥ 10 с) → congestion.
  • Событие обрезано клипом — начало 0.0 или конец = длительность. Сомнительные случаи — в notes с флагом, решаем арбитражем.
  • near_miss размечаем исчерпывающе: их окна бесплатны для Part B (кадры вокруг near-miss игнорируются метрикой).

6.6Двойная разметка, согласие, арбитраж

  1. Калибровка (Ч1–1.5). Все трое размечают одни и те же 60–90 с одного клипа, каждый в своём проекте. Для каждой пары — конвертация и evaluate.py, разбор каждого расхождения, заморозка гайдлайна v1.1.
  2. Двойная разметка (Ч1.5–4). Каждое видео размечают двое независимо, пары ротируются: A+B, B+C, C+A. Модель не показывается; после слепого прохода можно просмотреть кандидатов детектора, чтобы найти пропуски. Один проход ≈4–6× длительности видео (оценка).
  3. Согласие (Ч4–5). Разметка B оценивается как предсказания против A официальным evaluate.py, по классам и по каждому τ (F1 симметрична — одного направления достаточно). Цель — F1 ≥ 0.8 при τ = 0.5. Если по классу ниже ≈0.7 — правило неоднозначно, сначала чиним гайдлайн.
  4. Арбитраж. Третий человек в проекте gold импортирует X как аннотацию, Y как prediction и правит. Итог — dev_gt.json.
  5. IoU между аннотаторами для near_miss и коротких классов показывает реальный потолок F1@0.7; эта статистика идёт в EDA-карточку №16 на сайте.

6.9Proxy-набор аварий, синтетика, гигиена данных

Proxy-dev для аварий (в сэмплах аварий, скорее всего, нет)

  • 60–100 реальных клипов ACCIDENT с неподвижных CCTV (приоритет — городские перекрёстки сверху), затем TAD и CADP. START берём опубликованный (медиана 3–5 аннотаторов), END размечаем сами.
  • Плюс ≥ 2 ч нормального трафика как негативы.
  • Деление по камере или источнику, а не по клипам.
  • Проекция на тест: точность ≈ R·Nacc / (R·Nacc + FPrate·T). На сайте честно показываем обе величины.

Синтетические и инъекционные тесты

  • Животные, шины, коробки, вклеенные на дорогу на 10–60 с; дым из D-Fire поверх стоящей машины; автобус, перекрывающий стоящую машину.
  • Траектории, заданные вручную в метрах: ровно один сегмент с ожидаемыми границами.
  • Инъекция столкновений в треки сцены для Part B (§4.9).

Гигиена данных и лицензий

  • Разметка только локально или на своём сервере. Не загружать футаж организаторов в облачные сервисы: Roboflow Public публикует данные; CVAT Online на free-плане — 1 ГБ и нет командной работы; shared-проекты VIA идут через сервер VGG.
  • Модели для предразметки — только помощники; в репозиторий попадают, только если это выбранный детектор, и тогда указываются в README.
  • Использование закрытых моделей для предразметки dev — серая зона; считаем «нельзя», пока не ответят [орг.].
  • Не собирать записи с той же камеры другими путями. Перед обучением на краулинговых CCTV (ACCIDENT, TAD, CADP) проверить, что ни один клип не показывает место соревнования.
  • В README перечислить все датасеты и инструменты, которыми делали обучающие данные.
  • На сайте — без распознавания номеров и лиц, без ре-идентификации, без увеличенных кропов; публиковать ли сэмплы целиком — спросить [орг.].

  • Запрещено: видео той же камеры или перекрёстка, полученное другими путями. Не скрейпить YouTube, Telegram и городские камеры площадки. 7.6Лицензии и развилка AGPL против NC-SA

Развилка (решить командой до обучения; при сомнении — спросить организаторов; не юридическая консультация)

Ultralytics считает модели, обученные его кодом, AGPL-3.0, а AGPL не допускает дополнительных ограничений вроде «только некоммерческое». Чтобы не смешивать, вариантов два:

  1. (a) Учить Ultralytics-детектор только на данных без NC: наши кадры, аннотации COCO, D-Fire, Pyro-SDIS, MEVA, Street Scene (SA). NC-наборы (UA-DETRAC, MIO-TCD, ACCIDENT…) использовать для моделей вне Ultralytics (VideoMAEv2 — MIT-код).
  2. (b) Пермиссивный путь: RF-DETR (Apache-2.0) + trackers (Apache-2.0) и явная пометка NC-SA на веса.

SA-наборы (FASDD, Street Scene) требуют share-alike для производных данных; распространяется ли это на веса — юридически не решено. ND / no-redistribution (Cityscapes, CrowdHuman): данные и изменённые копии никогда не публиковать.

Тестовый набор

  1. Тестовые видео сняты в те же сессии и с той же установкой штатива, что сэмплы (18.09: C3896/C3897 днём, C3902/C3905 вечером)? Или в другие дни, с переставленной или перезумленной камерой?

  3. Сохраняется ли в тестовых файлах звуковая дорожка и можно ли использовать звук внутри detect_events (только Part A)?
  4. Как считается duration в скрытом GT: как CAP_PROP_FRAME_COUNT/fps (так делает харнесс) или по контейнеру?

Конвенции разметки

  1. Сливаются ли близкие, но не одновременные события одного класса? С какой точностью ставятся границы (в примере GT — целые секунды)? Есть ли минимальная длительность события?
  2. congestion: размечается ли обычная очередь на красный? Минимальная длительность? Относится ли правило «одновременные события — один сегмент» к пробке в двух направлениях?
  3. stopped_vehicle: считаются ли автобусы на остановке, такси при высадке, машины в парковочном ряду? Размечается ли машина, оставшаяся после аварии? Начало — в момент остановки (до истечения 10 с)?
  4. Машина пересекла стоп-линию на красный и остановилась до перекрёстка: только stop_line или также red_light? Как считаются красный+жёлтый и поворот направо по знаку 5.42?
  5. Разворот или поворот через сплошную размечается двумя метками (с solid_line_crossing)?
  6. jaywalking: считаются ли люди, выходящие из машины, полицейские, дорожные рабочие? failure_to_yield: считается ли случай, когда пешеход идёт на свой красный, а машина едет на зелёный?

  8. accident: END — только «все остановились или уехали» или включаются последствия? Водители, вышедшие на дорогу после аварии, — jaywalking? near_miss включает конфликты машина–пешеход и размечен исчерпывающе?
